# 待确认与补充问题

这些事项会改变用户资产、玩法和部署结果。文档中的建议不是已确认需求；
本轮初始化和保全不依赖它们，正式业务实现前需收敛关键项。

| 决策 | 建议起点 | 为什么要确认 |
|---|---|---|
| 农场归属 | 每个独立部署自有数据；群共享范围明确配置 | 决定注册唯一键、偷菜范围与迁移 |
| 多框架关系 | 先支持分别部署和迁移，不自动在线互通 | 联机会改变存储与服务架构 |
| 账号迁移 | 显式平台命名空间与人工确认映射 | QQ 官方标识与 OneBot ID 不宜自动合并 |
| 存量资产 | 默认保留并记录异常，另议补偿 | 旧逻辑有增发，无法从余额准确逆推 |
| 外部金币 | 真寻保留可选接入；其他框架默认关闭 | 外部钱包无法由本地事务保证原子性 |
| 点券和星级 | 先核对现有用途、成本与升级公式 | 涉及经济平衡与数据兼容 |
| 签到资源 | 首先保证内置/本地配置可用，联网更新可选 | 远程服务停机不应让基本玩法不可用 |
| 资源分发 | 精简基础资源；需要时使用固定版本扩展包 | 旧资源 ZIP 超 AstrBot 16 MB 市场限制 |
| 渲染 | 文本必备，图片可选且失败降级 | 宿主、字体、浏览器依赖和性能不同 |
| 兼容基线 | 保留旧指令清单；Python/宿主版本经矩阵实测确定 | 旧 README 的 3.10+ 不等于三框架共同最低版本 |
| 发布顺序 | 真寻先稳定，之后普通 NoneBot、AstrBot | 利用现有宿主验证闭环，控制变更范围 |
| 发布仓库 | 使用给出的三个现有仓库，接管前比较现有代码 | 三仓库不为空，不能直接覆盖 |
| 主仓库远程 | 已明确 Shu-Ying/main_plugin_farm | 本轮只建本地 Git，不误用发布仓库 |
| 发布授权 | 首次候选 PR 审查，稳定后再议自动发布 | 本轮未授权远程覆盖、推送或发布 |
| 跨平台 OS | 建议 Windows + Linux；macOS 有需求再验收 | 路径大小写、字体、浏览器和时区需分别测试 |
| 素材许可证 | 核对图片、字体、HTML 和借用工具来源 | 代码 GPLv3 不自动证明所有素材可分发 |
| 数据运维 | 定期备份、保留策略、恢复演练和脱敏诊断 | 游戏资产需要可恢复性和隐私保护 |

## 容易遗漏的技术约束

- 从旧仓库自动更新到新布局时，插件安装器是否删除旧文件；
  旧入口残留可能重复加载，必须进行“旧版→新版”真实升级演练。
- 多目标发布可能部分成功，需要按目标重试和状态清单。
- 插件降级不等于 schema 降级；必须定义最低可读写 schema。
- 网络重试、平台重复投递、图片发送失败不能再次发奖或扣款。
- 资源目录只读部署场景必须支持，把可写缓存放宿主数据目录。
- 同一宿主同时安装相关插件时，模块名称和第三方依赖可能冲突；
  插件私有打包只解决前者。
- Python、宿主框架、数据库 schema、作物规则和资源版本分别记录，
  不混用一个远程浮点版本比较所有兼容关系。
- 发布仓库里的现有 star、issue、tag 和许可证要保留；不能 force push。
- 子仓库是概念上的发布仓库，不使用 git submodule，也不把本地克隆
  提交进主仓库。
- CI 中的密钥不写源码；旧源码中暴露的服务令牌需服务端轮换。
